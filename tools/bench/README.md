# Стенды нативной сборки (build/native, build/native_strict)

Запуск из корня проекта: `node tools/bench/<имя>.js [...]`. Все без окна.

Скорость (комната по умолчанию 1,9; другая — `ROOM=ряд,столбец`, например `ROOM=5,7 node tools/bench/r19b.js`; работает в r19b/r19f/r19g/r19h/r19L/r19site/r19reg):
- `r19b.js` — комната 1,9 (3 черепа, огонь, 2 ленты; телепорт, бессмертие, Джо стоит): кадров на шаг, шагов/с. **Главная метрика.** `B=<папка сборки>` — другая сборка.
- `nsteps.js build/native` — обычная игра (ходьба по плану), шагов/с.
- `rsplit.js build/native` — обычный шаг отдельно от смены комнаты.
- `r19f.js` — такты по процедурам с вложенными (`W=disp_prep,crit,...`), на вызов и на шаг.
- `r19g.js` — плоский профиль внутри процедуры (`P=force_live_t`).
- `r19L.js` — профиль по контекстам: L логика, D подготовка вывода, I прерывание.
- `r19h.js` — такты на шаг, простой (ожидание кадра), прерывание.
- `r19site.js` — такты вызовов по местам вызова (`P=cpir,L_9159 R19=1`).
- `r19reg.js` — такты по участкам кода (`REG="имя:метка_от:метка_до,..."`).
- `pschk.js` — сколько готовых сдвигов врагов поместилось (см. docs/NATIVE_VIDEO.md).
- `sktrace.js`, `attrchg.js` — как часто меняются место и кадр спрайтов.

Правильность (должно быть 0 ошибок):
- `scrchk.js build/native 2000 [r19|tp]` — весь экран против эталона: фон по VNT + нарисованные слои объектов (spr_rec); исходная графика MSX — video-ref.js, независимо от кэша Вектора. Проверяется также экран сразу после crit; устаревшая запись dlist не исключает экран, если в PND уже нет ожидающих клеток. Снимок IRQ внутри изменения карты/цветов исключается по video_edit; на каждом L_A5D1 отдельно требуется video_edit=0.
- `cellchk.js build/native 3000 [tp]` (env `FANY=1`, `R19=1 EVERY=1`) — клетки без спрайтов против карты.
- `native-video.js [build/native] [1200]` — точность и неизменяемость готовых сдвигов; скачок катящихся врагов ≤3 пикселей, отставание и расстояние, частоты фаз огня/лент.
- `slsall.sh` — сверка логики с MSX (lockstep) по сборке `build/native_strict` (собрать с `-DSTRICT`). Норма: в каждой строке только `тик 0: 1 байт: 7048=0/1` (старт с меню) и «VRAM совпадает по всем тикам».

Логика:
- `rooms.js` — все 99 комнат каждого из трёх уровней. `B=build/native`,
  `LV=1` (иначе все уровни), `WARM=64`, `N=128`, `OUT=build/rooms.json`.
  Столбцы: уровень, ряд/столбец, шаги/с, logic, display (подготовка), irq,
  idle. Такты IRQ, включая выдачу подготовленного экрана, указаны отдельно.
  Герой бессмертен; после телепорта сохраняется входная поза и восстанавливается
  между полными шагами (состояние 0), чтобы падение/лента не унесли его в другую
  комнату. Это воспроизводимый неподвижный пробник, а не сценарий прохождения.
  Смена комнаты и 64 шага прогрева не входят в измерение. Во время обхода
  сборку не менять. Для сравнения сохранять отдельные каталоги сборок.
- `r19L.js` теперь раздельно считает L (логика, включая обработчик кадра),
  D (disp_prep), I (IRQ) и W (цикл ожидания). Смена стека внутри IRQ и frame_wait
  учитывается по адресам возврата; такты относятся к предыдущей команде.
- `logic-check.js build/logic-before build/native` — прямая сверка машинного
  кода до/после: все 256 значений классов и 65536 пар координат, включая
  переполнение и вложенные чтения. Исходную сборку надо сохранить до изменения.

Стенды используют корень своего checkout; их можно запускать в worktree.

`r19f` и `r19site` также сопоставляют возврат по PC **и** SP: временный
стек IRQ больше не обрывает измеряемую процедуру. `cpir` входит в собственную
метку на каждой итерации; повторный вход с тем же SP не считается новым вызовом.
Поэтому исправленный профиль исходной версии отличается от старых цифр
в TASK_LOGIC_OPT. Вложенные процедуры учитываются включительно; их строки
нельзя складывать. `r19L` даёт независимую полную стоимость логики.

`logic-check` дополнительно проверяет 11264 сочетания состояния/тайла/шага
конвейера, 512 вариантов ввода, опоры и смертельные тайлы, 5000 состояний
врагов с допустимыми фазами, а также неизменность таблицы классов при загрузке.
`tools/unit.js` поддерживает `B=build/native_strict` и нативные `room_colors`
без отсутствующих регистров VDP.

`rooms.js`: `FREE=1` оставляет героя свободным (без возврата входной позы),
`HIDE_JOE=1` обнуляет оба цвета на границе вывода для контрольного сравнения;
`N=600 WARM=64 LV=1|2|3 OUT=...` задают окно и JSON с распределением кадров.
Без LV проверяются все 297 комнат. Без FREE сохраняется прежний фиксированный
сценарий. В `nsteps` печатаются распределение кадров и отдельно интервалы с
полной перерисовкой комнаты и без неё. `INPUT=1` у r19f добавляет ходьбу,
прыжки и лестницы, `DETAIL=1` — максимальную стоимость вызова.

### Джо NES и переходные кадры

- `FRAMECHECK=1 node tools/bench/scrchk.js build/native 2000 tp` — все клетки после каждого возврата из crit, включая продолжения и вызовы вне IRQ. Фон отслеживается по действительно переданным тайлам/цветам; нет общего пропуска по pending.
- `FRAMECHECK=1 B=build/native DIR=build/play OUT=nes node tools/bench/play.js 1 0 8` — вместе с FPS пишет sidecar `nes_frames_1_0.json` и `nes_joe_1_0.json`.
- `B=build/native node tools/bench/scanout.js` — фактические чтения лучом, поиск переходного синего индекса 2. `FROM=420 TO=600 OUT=build/joe_nes/scan` сохраняет выбранные кадры растра без окна.
- `SCENE=walk|ladder|rope|jump|death B=build/native node tools/bench/joe-scenes.js` — клавиатурные сценарии; rope начинает на существующем шесте стартовой комнаты, затем работает обычная физика. OUT сохраняет индексированные кадры. Death спускается с лестницы и попадает под врага; ladder разворачивается до схода на конвейер.
- `B=build/native node tools/bench/joe-poses.js` — отдельная фикстура вывода всех 23 NES-поз, обоих зеркал и восьми сдвигов (368). Это проверка графики, не замер физики. `PROFILE=1` дополнительно измеряет подготовку, восстановление и вывод всех вариантов. `FORCE80=1` принудительно выбирает полный путь трёх плоскостей, сохраняя тот же ожидаемый растр.
- `B=build/native node tools/bench/joe-selector.js` — 1314 проверок соответствия игровых состояний всем 23 NES-позам, включая лестницу в обоих направлениях и перестановку MSX-слоёв. `joe-scenes` в режиме `ladder` разворачивает движение на лестнице и требует обе фазы NES при подъёме и спуске; прежний выбор боковой стойки вызывает ошибку даже при правильных пикселях этой стойки.
- `B=build/native ROOM=7,2 OUT=build/joe_nes/room node tools/bench/joe-shot.js` — снимок VRAM с фактической палитрой.

Эталон `joe-ref.js` независимо читает CHR и OAM из NES ROM, не готовый образ F900. Генератор: `python3 tools/nes/joe_native.py --height 23`. По решению владельца итоговая сборка использует натуральные 22–23 строки. Вариант `--height 19` остаётся для сравнения скорости; флаг `NES_JOE_PALETTE` меняет палитру, дополнительный `NES_JOE_3COLOR` включает розовый индекс 2.

`python3 tools/nes/joe_media.py` строит PNG сравнения палитр и GIF из
индексированных снимков `joe-shot`, `joe-scenes` и фактического растра `scanout`.
