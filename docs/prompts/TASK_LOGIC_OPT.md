# Задача: ускорение логики игры (нативная сборка Montezuma's Revenge для Вектора-06Ц)

## Контекст

Проект `~/projects/monty-v06c`, линия `src/native` (i8080, 3 МГц, кадр 59 904 такта при 50 Гц). Цель проекта — **1 шаг логики на кадр (50 шагов/с) во всех комнатах**.

Вывод уже переделан без эмуляции VDP: `docs/NATIVE_VIDEO.md`, `docs/prompts/TASK_NO_VDP.md`. По последнему замеру комната 1,9 даёт 50 шагов/с впритык. Логика по прежнему профилю стоит **19–25 тыс. тактов на шаг**, это треть кадра и самый крупный кусок, который ещё не трогали. Ускорение логики даёт запас во всех тяжёлых комнатах.

Как устроена логика:
1. По разбору MSX-версии (`docs/DISASM.md`, Ghidra/SkoolKit) написана JS-модель `src/model`, совпадает с MSX (`tools/modelcheck.js`, `tools/optcheck.js`).
2. По модели вручную написан код i8080 (`src/native`: `main.asm`, `hero.asm`, `enemy.asm`, `collide.asm`, `frame.asm`, `drawroom.asm`, `block.asm`, `tiles.asm`, `level.asm`, `sound.asm`, `screen.asm`).
3. Каждый модуль сверялся с моделью (`tools/unit.js`), вся игра — сверкой lockstep с MSX: ОЗУ игры 7000–73FF совпадает тик в тик.

Ручных оптимизаций пока мало:
- `cpir`: искомое держится в A;
- быстрый путь `L_916C` (тайлы под объектом) до клетки 2DDh.

Прочитай: `docs/NATIVE.md`, `docs/DISASM.md`, `docs/NATIVE_VIDEO.md`, `tools/bench/README.md`, заголовки модулей логики.

Сборка (из `src/native`):
```
../../tools/sjasmplus --nologo --i8080 --sym=../../build/native/monty.sym game.asm
../../tools/sjasmplus --nologo --i8080 -DSTRICT --sym=../../build/native_strict/monty.sym game.asm
```

## Цель

Снизить такты логики на шаг: в комнате 1,9 и в «худших по логике» комнатах — **в 1,5 раза и больше**, без изменения поведения игры.

## Жёсткие правила

1. **Поведение не меняется.** Сверка `sh tools/bench/slsall.sh` по `build/native_strict` после каждой правки. Норма: в каждой из 4 строк только `тик 0: 1 байт: 7048=0/1` (особенность старта с меню) и «совпадает по всем тикам». Любое другое расхождение — откат.
2. **`-DSTRICT`** — сборка «как у MSX». Допуски у лестниц и предметов (`IFNDEF STRICT` в `hero.asm`, `collide.asm`) есть только в обычной сборке. Оптимизируй обе ветки. Допуски по смыслу не менять.
3. **Память впритык.** Рост кода съедает место готовых сдвигов врагов: проверка `node tools/bench/pschk.js`, на старте ~74 из 96. Таблицы ради скорости — только если окупаются; каждое снижение числа сдвигов обосновать замером.
4. **Вывод и прерывание не ломать.** `display.asm`, `sprites.asm` и т. п. трогай, только если логика с ними связана (уведомления о смене клеток `map.asm`). После правок — эталон экрана `tools/bench/scrchk.js` (0 ошибок: обычная игра, `r19`, `tp`).
5. Если параллельно в этом же каталоге работает другой агент (вывод, графика NES) — работай в отдельном `git worktree` и коммить только свои файлы.

## Как действовать

1. **Замер исходного состояния.**
   - Такты логики на шаг по процедурам с вложенными вызовами и по местам вызова: `tools/bench/r19site.js` (`P=... R19=1`), `r19f.js` (`W=...`), `r19reg.js`, `r19L.js`. Учти, что `frame_wait` теперь «кадр → обработчик → подготовка вывода», поэтому разбивка контекстов в `r19L.js` может требовать правки.
   - Сделай стенд, который обходит **все комнаты** трёх уровней (телепорт `71A7`/`71A8` + `7079:=9`, бессмертие как в `r19b.js`) и печатает по каждой: шаги/с, такты логики на шаг, такты вывода на шаг. Список самых медленных комнат — главный ориентир.
2. **Горячие места**, известные по прежнему профилю комнаты 1,9 (перепроверить):
   - `L_88D1` (процесс героя с врагами) ≈ 12 тыс. тактов на шаг;
   - цикл врагов `L_A7A1`/`en_*` ≈ 7 тыс. на трёх черепах: `L_9159` ≈ 1 тыс. на вызов, вызывается для каждого врага;
   - `L_A894` — поиск среди 8 «стен», 4 раза на шаг;
   - `cpir` по разным таблицам (`it_is`, `p8f2`–`p8f4`, `L_913B`, `L_8F37`, `L_908F`) ≈ 2,3 тыс.;
   - `hero_state` ≈ 2 тыс., `L_8DE8` ≈ 1 тыс.;
   - обработчик кадра ≈ 1 тыс., главный цикл процессов (`main.asm`).
3. **Приёмы** (выбирай по замеру):
   - таблицы принадлежности вместо линейного поиска (тайл → класс: предмет, стена, смертельный…). Строить при старте из тех же данных картриджа, в свободных байтах страниц;
   - чтение тайлов под объектом без промежуточного буфера и без лишней возни с `70AF`/`705F`, если её чистый эффект совпадает;
   - переменные в регистрах, а не в памяти; общие подвыражения; развёртка коротких циклов;
   - специализация частых случаев (враг без смены направления, герой стоит);
   - убрать повторные вычисления в пределах шага.
4. **JS-модель для проверки идей.** Прежде чем переписывать ассемблер, можно проверить новый алгоритм участка в модели (`src/model`): состояние после тысяч шагов должно совпасть с исходной моделью (`tools/optcheck.js`). Потом переносить в i8080. Отдельные модули сверять `tools/unit.js`.
5. **Каждая правка:** сборка (обе), `slsall.sh`, `scrchk.js` (3 режима), `r19b.js`, обход комнат, `pschk.js`. Отдельный коммит, сообщение по-русски с цифрами до/после.
