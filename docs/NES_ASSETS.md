# Графика NES Montezuma’s Revenge → Вектор-06Ц

Разбор локального `orig/nes/monty.nes`, 27.10.2026. ROM — главный источник; видео и шумные вырезки не использовались. Изменений в `src/native` нет. Графика не внедрена в игру.

Выгружены **512 CHR-плиток, 99 комнат, 53 ссылки на кадры метаспрайтов (106 изображений с двумя направлениями), 1782 случая палитры**. У Джо 12 состояний и 23 ссылки на кадры, включая пустой кадр. Совпадающие рисунки намеренно не удалены: сохраняются номера и порядок фаз оригинала.

Главные листы (всё локально, `build/` уже исключён из git):

- `build/nes/chr/gray.png` — все 512 плиток с номерами; `background_0..3.png`, `sprite_0..3.png` — те же плитки в игровых палитрах стартовой комнаты.
- `build/nes/sprites/{joe,snake,skull,spider,bat}_sheet.png` — все фазы и оба направления; отдельные PNG имеют родное разрешение и прозрачность.
- `build/nes/tiles/{terrain,animations,items,doors,observed}.png` — именованные группы, фазы, предметы, двери, все наблюдавшиеся сочетания «плитка + палитра».
- `build/nes/{palettes,floors}.png`, `rooms/pyramid.png`, `rooms/room_00..98.png` — палитры и комнаты.
- `build/nes/mockups/{msx_joe_mapping,msx_enemy_mapping,joe_choices,overview}.png` — сопоставления и варианты Вектора.
- `build/nes/data/*.json` — индексы пикселей, части метаспрайтов, рамки/занятые размеры/цвета каждого кадра, потоки RLE, таблицы имён/атрибутов, палитры и сопоставления. `manifest.json` перечисляет файлы и входы MSX.

## Воспроизведение и границы проверки

Из корня проекта, Python 3.10+ и Pillow (`tools/nes/requirements.txt`):

```sh
python3 tools/nes/extract.py orig/nes/monty.nes build/nes/
python3 tools/nes/verify.py orig/nes/monty.nes build/nes/

# Независимая проверка через MAME, без окна:
python3 tools/nes/capture.py orig/nes/monty.nes build/nes/reference
python3 tools/nes/verify.py orig/nes/monty.nes build/nes/ --reference build/nes/reference

# Обычная игра: только кнопки контроллера, без подстановки поз/комнат:
python3 tools/nes/live_capture.py orig/nes/monty.nes build/nes/live
python3 tools/nes/verify_live.py orig/nes/monty.nes build/nes build/nes/live
python3 tools/nes/verify_bat.py orig/nes/monty.nes build/nes/data/bat_verification.json
```

Основная выгрузка требует только NES ROM и Pillow. Для сравнения с MSX и макетов с настоящей геометрией MSX дополнительно используются уже существующие `build/res/{sprites,tiles,colors}.bin`, `build/res/rooms_L1.json`, `build/monty_entry.bin`. Они были доступны в этом прогоне. При их отсутствии создаются только иллюстративные макеты с ужатым полем NES; это явно записывается в `manifest.json`. Сравнительные листы MSX в таком случае не создаются. Подготовка исходных ресурсов MSX описана в `docs/DISASM.md` и `tools/export_res.py`.

`cpu.py` исполняет документированные команды 6502 и нужные обращения к PPU без моделирования тактов, прерываний и APU. Он вызывает оригинальные процедуры разбора комнат и палитры. Отдельный прямой декодер RLE сверяется с исполнением ROM для всех 99 комнат. Недокументированный opcode или зависание вызывает ошибку.

MAME сначала запускает обычную игру и снимает стартовую комнату. Затем небольшая обвязка заменяет **только главный цикл в эмулируемой памяти**, выключает NMI/показ и вызывает исходные процедуры ROM для 99 комнат. Файл ROM не меняется. Снимки не являются прохождением всех комнат: это независимая проверка процедур на настоящем ядре 6502/PPU MAME. Проверяются все 768 клеток поля, атрибуты его квадрантов и все 16 значений фоновой палитры. В обычном игровом снимке допускается только различие фаз известных анимированных плиток; квадранты HUD исключены из сравнения. Полный результат — `data/verification.json`.

Кроме этого проверяются обратная упаковка всех 512 CHR-плиток, 106 вариантов OAM против оригинальной процедуры `$C40F` и ограничение макетов восемью индексами. Палитры 1782 случаев вычислены исходным кодом ROM; независимая MAME-сверка покрывает исходный уровень сложности, без факела. Эта первая проверка не покрывала прохождение и столкновения. Проверка обычной игры добавлена ниже; новый вывод Вектора не внедрён и не тестировался.

## ROM, адреса и форматы

SHA-256: `453a6a9198b11cf6f948f5b61ab98dd7e6fbf7928a7b257941d4f5e7aa4a54fb`.

Размер 40976 байт, заголовок `4e45531a020101080000000000000001`: NES 2.0, NROM/mapper 0, вертикальное зеркалирование, без trainer. PRG: файловые `$0010–$800F` → CPU `$8000–$FFFF`; CHR: файловые `$8010–$A00F`. Для адреса PRG: **смещение файла = CPU − `$8000` + `$10`**. Ниже все адреса с `$` — CPU, если не оговорено иное.

| Адрес | Назначение |
|---|---|
| PPU `$0000–$0FFF` | 256 плиток спрайтов, CHR-номера `000–0FF` |
| PPU `$1000–$1FFF` | 256 фоновых плиток, CHR-номера `100–1FF` |
| `$C601` | 100 little-endian указателей на RLE комнат |
| `$C6C9` | 100 указателей на RLE таблиц атрибутов |
| `$C791` | 100 указателей на дополнительные объекты/врагов |
| `$C859` | смещение номера комнаты при переходе между этажами: `00 02 04 … 12` |
| `$D738` | 12 указателей на состояния Джо |
| `$D77C`, `$D868`, `$D908`, `$D990` | таблицы змеи, черепа, паука, летучей мыши |
| `$D45F–$D486` | короткие таблицы фоновых и спрайтовых палитр |
| `$C5D5–$C5DD` | 9 цветов акцента этажа/сложности |
| `$C599–$C5C0` | номера фаз анимации фона |
| `$D28B–$D2A6` | семь рисунков предметов 2×2 |
| `$C5C9`, `$C5CD`, `$C5D1` | по 4 номера плиток открытых дверей |

CHR: 16 байт на плитку, строки младшей битовой плоскости 0–7, старшей 8–15; левый пиксель — бит 7. Индекс цвета `lo | hi<<1`. `tiles.json` содержит все 64 индекса каждой плитки, PPU-адрес и файловое смещение.

Метаспрайт — последовательность **`dy, tile, attribute, dx`**, конец — `$FF` на месте следующего `dy`. Это порядок OAM, а не XY-пар. Смещения интерпретируются как знаковые при нормализации рамки. Атрибут: биты 0–1 — одна из четырёх палитр спрайтов, 5 — позади фона, 6/7 — отражения X/Y. Банк спрайтов — `$0000`, размер аппаратной части — 8×8 (`PPUCTRL=$90`). Экранный Y аппаратного спрайта равен записанному OAM Y + 1.

Состояние анимации: **`число кадров, задержка, 4 байта области столкновений, указатели кадров[]`**. Процедуры `$C355/$C3BB` выбирают анимацию/фазу, `$C40F` собирает OAM. При направлении 1 используются исходные данные; при другом направлении каждая часть получает `dx := 8−dx`, `attribute XOR $40`. Из-за якоря отражённая рамка может иметь другой минимум X: нельзя просто менять флаг плитки, оставляя части на прежних местах.

Пример: Джо `$D738[0] → $D4A0 → $D487`: шесть частей, сетка 2×3, номера `$15,$16 / $17,$18 / $1B,$1C`, атрибут 0, смещения X 0/8 и Y 0/8/16. Прозрачные края дают занятую область **16×22** внутри ячейки 16×24.

## Палитры и RGB

NES хранит номера цветов, а не RGB. Здесь зафиксирована [стандартная палитра FCEUX](https://github.com/TASEmulators/fceux/blob/master/src/palettes/palettes.h), таблица `palette`, первые 64 цвета, преобразование `P64(v)=(v<<2)|(v>>4)`. Это конкретная воспроизводимая интерпретация сигнала 2C02; другого единственного «точного RGB 2C02» не предполагается. Полные 64 RGB записаны в исходнике и `rom.json`. Назначение стандартной палитры подтверждено [документацией FCEUX](https://fceux.com/web/help/PaletteOptions.html). Цветовые акценты NTSC, аналоговый декодер, gamma и эмуляция emphasis в PNG не моделируются; игра запускается с обычной маской `$1E`.

| Номер NES | RGB | Применение |
|---|---|---|
| `0F` | `#000000` | фон/прозрачность |
| `06` | `#A60000` | тёмный цвет Джо |
| `26` | `#FF7561` | светлый красный Джо |
| `27` | `#FF9A38` | кожа/шляпа Джо |
| `16` | `#DB2800` | красный фона |
| `1C` | `#00828A` | сине-зелёный фона |
| `19` | `#009600` | змея |
| `17` | `#CB4D0C` | паук |
| `20` | `#FFFFFF` | череп |
| `10` | `#BEBEBE` | летучая мышь |

Запись палитры — `$2006` с адресом `$3F00–$3F1F`, затем `$2007`. `$AC9A` сначала заполняет её `0F`; `$AC54` задаёт спрайтовые палитры, `$ACEB/$AD97` — фон. В стартовой комнате без мигания:

| PPU | Цвета | Источник |
|---|---|---|
| `3F00` фон 0 | `0F 16 27 1C` | `$D473`, затем акцент `$C5D5` |
| `3F04` фон 1 | `0F 20 16 1C` | `$D46F` |
| `3F08` фон 2 | `0F 16 27 1C` | `$D46B`, затем акцент |
| `3F0C` фон 3 | `0F 20 16 1C` | `$D467` |
| `3F10` спрайты 0 | `0F 26 06 27` | `$D477`, Джо |
| `3F14` спрайты 1 | `0F 19 17 20` | `$D47B`, змея/паук/череп |
| `3F18` спрайты 2 | `0F 10 0F 0F` | `$D45F`, мышь |
| `3F1C` спрайты 3 | `0F 0F 0F 0F` | после очистки |

В палитре спрайтов цвет 0 прозрачен. Зеркала `$3F10/$14/$18/$1C` на `$3F00/$04/$08/$0C` учтены. Для фонового индекса пикселя 0 всегда используется общий `$3F00`, независимо от атрибута.

Цвет акцента: **`C5D5[(этаж_NES + уровень_внутренний) % 9]`**, ставится в `$3F02` и `$3F0A` (`$AF2A`). Внутренний уровень 0 соответствует первому уровню игры. При уровне 0:

| Этаж NES | Ряд MSX | Акцент NES |
|---|---|---|
| 1 | 0 | `27` |
| 2 | 1 | `2B` |
| 3 | 2 | `05` |
| 4 | 3 | `25` |
| 5 | 4 | `21` |
| 6 | 5 | `1B` |
| 7 | 6 | `13` |
| 8 | 7 | `3D` |
| 9 | 8 | `06` |

Темнота — `$AD7E`: если в инвентаре `$D3–$D7` нет предмета `$0C` (факел) и этаж ≥ порога `$07C0`, фон 0 становится чёрным через `$C867`, фон 3 также скрывается. Начальный порог 9, при смене уровня уменьшается до минимума 1 (`$BB2B`): для внутреннего уровня `L` это `max(1,9−L)`. Некоторые предметы остаются видимыми в других фоновых палитрах; темнота не означает обнуление всех 32 цветов. Факел возвращает фон.

Комнаты 89, 90, 91 имеют дополнительную замену `$3F02/$3F0A` на `06`, когда темнота не действует (`$ACF5–$AD28`). Поэтому один цветовой ряд на этаж не исчерпывает всех вариантов. `palettes.json` содержит точные 32 номера для каждой комнаты, уровней 0–8 и обоих состояний факела.

Ещё два изменения во время игры: `$8B12` циклически меняет `$3F17` через `$C5C1` (цвет черепа), а неуязвимость через `$8B2A/$C5C5` меняет три цвета палитры врагов. При паузе (`$07FD` положителен) процедуры фона понижают яркость на `$10`, если результат не отрицателен; спрайты скрываются. Эти временные фазы не выдаются за отдельные базовые палитры этажей.

## Джо, враги и двойная ширина

Джо: стойка `00`, ходьба `01` (4 фазы), падение после смертельного срыва `02` (2), прыжок/обычное падение `03`, лестница `04` (2), положения на канате/шесте `05/06/0A`, выход с лестницы `07`, исчезновение `08` (5), невидимость `09`, разлёт `0B` (3). Движение по конвейеру использует обычные позы; отдельной анимации «конвейер» в таблице нет. Названия состояний даны по местам вызовов и виду рисунка, не взяты из исходников автора NES.

Обычные позы имеют сетку **16×24**, занято **16×22**, на лестнице/канате **16×23**. Гибель использует также сетки 16×16, 32×24 и 32×32. Во всех обычных позах палитра `06,26,27`; поздние кадры эффектов могут содержать меньше цветов. Полный каталог каждого кадра с адресом и цветами приведён ниже и в `metasprites.json`.

Змея — 2 кадра (14×13 занятых точек), череп — 12 кадров (14×14…16×11), паук — 8 кадров (16×12…16×10). Летучая мышь — 8 кадров, ячейки 16×8/16×16, занято до 16×9; запускается отдельными процедурами `$B1FF/$B268/$B293`. Это дополнительный враг NES, прямого аналога в MSX нет. Змея в NES является метаспрайтом, в MSX — фоновым объектом.

**Проверка пар пикселей:** во всех непустых кадрах Джо 2317 из 2317 затронутых горизонтальных пар одинаковы, включая цвета и прозрачность. У паука и мыши также 100%; у черепа около 70,2%, у змеи 30%. Во всём CHR лишь 64,5% затронутых пар совпадают. Значит, «двойная ширина» — свойство части рисунков, а не режим PPU. Джо допустимо редактировать как 8 логических столбцов с удвоением по X; автоматически делить ширину всех ресурсов пополам нельзя.

## Проверка кадров по обычной игре (TASK_NES_ASSETS_2)

Проведено **10 воспроизводимых прогонов MAME без окна**, только кнопками контроллера. Не подменялись ROM, комнаты, игровая RAM, номера поз или OAM. Маршруты собирают белый ключ, проходят комнаты 2→1→5→4→10→11→12; отдельный маршрут идёт через комнату 6 обратно на канат комнаты 5. Условные нажатия в длинном маршруте позволяют дождаться выключения лазера, прыгнуть за мечом и зацепить шест. Условия записаны в `plan.json`, фактические кнопки — в `trace.tsv`.

Результат: **1583 экранных снимка, 3372 проверки объектов, 0 расхождений**. Все **53 ссылки на кадры** наблюдались в игре. Для Джо проверены **43 из 46 направленных вариантов**, для всех объектов вместе — **87 из 106**. Недостающие 3 варианта Джо — только правый `0B`: `$A5B4–$A5BB` принудительно задаёт направление 0, то есть отражённый вариант. У обычной мыши направление фиксировано 1; у паука здесь наблюдалось направление 1. Все 106 вариантов дополнительно проходят исходную проверку OAM через `$C40F`, но она не объявляется живым прохождением.

Проверка состоит из трёх независимых сопоставлений:

1. Части из `metasprites.json` сравниваются с фактическими байтами DMA, включая положение, тайлы, атрибуты, отражение, число частей и порядок.
2. Все 87 наблюдавшихся отдельных PNG сравниваются с CHR, размещённым по **живому OAM**, с проверкой всей рамки: ошибочно обрезанная шляпа не могла бы пройти эту проверку.
3. Вся прямоугольная область объекта, включая прозрачные места, фон и другие объекты, сравнивается с реальными пикселями `screen:pixels()`. Учитываются приоритет, отражения, клиппинг и предел восьми аппаратных спрайтов на строку. Координаты и цвета не подгоняются. RGB берётся из независимого устройства палитры MAME; PNG каталога используют зафиксированную палитру FCEUX, поэтому сравнение проходит через номера NES-цветов и текущую игровую палитру, а не через равенство RGB двух разных эмуляторов.

У MAME есть существенная особенность синхронизации: в `frame_done` последний DMA уже принадлежит следующему экранному кадру. Для снимка сохраняется предыдущий DMA; PPU-память берётся после всех записей соответствующего NMI, перед `$C597` (RTI). Чтение палитры непосредственно на DMA давало расхождения только на тактах смены цвета черепа. Эти ошибки наблюдения устранены до финальной сверки; ни один пиксель не исключён как «почти совпавший».

Состояние селектора — `$1C+s`, указатель текущего кадра — `$34+s:$2E+s`, направление — `$40+s`, следующий индекс — `$58+s`. `$C3BB` увеличивает индекс после выбора, поэтому `$58` нельзя подписывать как текущую фазу. Более того, `$1C` бывает `$FF`, когда текущий рисунок заморожен. В `live_verification.json` сохранены и сырой селектор, и следующий индекс, и фактически выбранные состояние/фаза, однозначно установленные по указателю из `$D738`.

**Ошибка сборки `03:0` и `04:0` не подтвердилась.** Живой OAM и экран совпали с выгрузкой. У `03:0` (`$D54E`) верхние части — `$15/$16` при dy=0; у `04:0` (`$D56F`) — `$24/$25`, затем `$26/$27` и `$28/$29`. У первой лестничной позы подняты руки; рисунок шляпы отличается от стойки. Ошибка была в листе: подпись следующего ряда находилась сразу под картинками предыдущего, а подпись самой картинки — над ней. `sheet()` теперь ставит подпись **снизу в пределах своей рамки**. `joe_sheet.png`, `joe_choices.png`, сопоставления MSX и остальные листы перегенерированы. Сами таблицы метаспрайтов и их отражение не менялись.

Ниже для каждого кадра указаны первые точные совпадения экрана/OAM/PNG; номера относятся к профилям `build/nes/live/`. В каждой ячейке сохранены `.png`, `.ram`, `.oam`, `.ppu`, `.shadow`, `.pixels.z`. Полный список повторных проверок — `data/live_verification.json`. `live/joe_verified.png` — реальные экранные вырезки с подписями, без удаления окружающего фона. ## Фон, предметы и анимация

Экран NES — **32×30** клеток (256×240). HUD занимает 6 строк, поле — **32×24** с PPU `$20C0`, высота 192. MSX/порт — весь экран 32×24 (256×192), HUD 5 строк и поле **32×19**, высота 152. У NES своя растровая раскладка: это не готовая таблица имён MSX. Номера комнат и пирамидальная топология соответствуют; координаты и высокие лестницы/провалы требуют адаптации.

Нормальные комнаты — индексы 0–98. Для этажа `F=1..9`: номера от `F²−1` до `(F+1)²−2`. Ряд MSX `r=F−1`; столбец `c=index−r(r+2)+8−r`. Таким образом, **комната `(1,9)` — индекс 5 / этаж NES 2**, стартовая **`(0,10)` — индекс 2 / этаж NES 1**. В таблицах есть ещё слот 99; он сохранён как дополнительный указатель, его игровой смысл здесь не утверждается.

Поток `$B79E` чередует пакет буквальных байтов `N, bytes[N]` и повтор `N, value`; `FF` на месте длины завершает поток в любом состоянии. Нулевая буквальная длина сразу переключает состояние, нулевая повторная длина означает 256 повторений по поведению `DEX`. Поток комнаты даёт 768 байт, атрибутов — 64. Процедуры `$BE5E/$BE8C` пишут поле и атрибуты, `$92B1` добавляет предметы/двери/изменения тайлов. В `rle_streams.json` — исходные сжатые байты и прямой результат; `rooms.json` содержит окончательные таблицы после объектов.

Атрибутный байт задаёт четыре палитры для квадрантов 16×16. Для клетки `(tx,ty)` адрес атрибута `$23C0 + 8*(ty//4) + tx//4`, сдвиг `4*((ty%4)//2)+2*((tx%4)//2)`. Поэтому при переносе нельзя трактовать NES как «один цвет на группу из восьми тайлов» MSX.

Именованные группы используют номера фоновой таблицы (прибавить `$100` для общего номера CHR): кирпич/пол `00–03`, канат/цепь `0C/0D`, лестницы `0F–14`, платформы `15/16`, пустота `17`, огонь `18–1F`, факел `23–2C`, вертикальный лазер `2D–34`, горизонтальный `35–38`, закрытые двери `39–3B`, конвейеры `3C–47`, открытые двери `56–61`. Полная карта контекстов цвета — `background_usage.json`; лист `terrain.png` показывает формы в единой палитре для сравнения.

Предметы не относятся к OAM, это фоновые блоки **16×16**:

Формы ключей различаются, поэтому определять их только по одному предпросмотру без атрибутов ошибочно. `items.png` использует реальные палитры найденных комнат; координаты всех найденных экземпляров есть в JSON. Дверь закрыта — 8×32 (одна плитка четырьмя строками), открыта — **24×32**: три верхние плитки и повтор четвёртой в прямоугольнике 3×3 (`$94EB/$9596`). Это отличается от открытой двери MSX 16×32.

`$8B48` — диспетчер 11 шагов обновления; пустые группы он пропускает. Поэтому огонь **не имеет универсального периода «каждые N кадров» для всех комнат и нагрузок**. В обычном старте MAME зафиксированы 11 последовательных интервалов по **5 кадров**, примерно 12 смен/с при 60 Гц, цикл 20 кадров. Сложные перестройки/обновления интерфейса могут задерживать диспетчер. У лазеров также есть циклы включения: горизонтальный — 110 кадров включён / 21 выключен (`$BD00`), вертикальный — 93/93 (`$BCCF`), в выключенном состоянии используется `17`. Для остальных комнат отдельно измерять диспетчер не потребовалось: данные фаз и код частот извлечены, фактический темп огня при нагрузке оставлен явным ограничением.

`rooms/room_*.png` показывает фон и фоновые предметы, без OAM и без HUD (48 верхних строк оставлены чёрными). Это каталог растровой геометрии, не скриншот полного кадра игры.

## Сопоставление с MSX

Сопоставление проверено по выбору кадров `$92DC`, таблицам исходного MSX-снимка `$9378–$93AD` и их переносу в `src/native/collide.asm` (только чтение). `$8DE8` в `hero.asm` применяет движение; собственно выбор номера спрайта выполняется в `$92DC/$9305`. Состояние — `$7079`, фаза обычной анимации — `$70AA >> 1`, направление — результат `$9369`. Здесь сопоставляется **смысл**, а номера фаз разных рисунков предлагаются для переноса, не объявляются исторически общими.

`mapping.json` теперь содержит `msx_states`, адрес таблицы, фазы, направление и отдельную политику неоднозначных случаев. На сравнительном листе подписи стоят **под своей картинкой**, каждая ячейка отделена рамкой. **Шесть поз ходьбы MSX — это три уникальных рисунка в каждую сторону**, а не шесть последовательных фаз. Таблицы: вправо `34/98, 6C/A0, 34/98, 34/9C`, влево `40/A4, 7C/AC, 40/A4, 40/A8`. Четырёхфазный счётчик можно сохранить, заменив все четыре позиции на четыре фазы NES; фаза 2 перестанет повторять фазу 0. Для полного темпа оригинала NES нужен отдельный визуальный счётчик с задержкой 6 игровых шагов, без изменения физики MSX.

У лестницы четыре MSX-индекса повторяют два рисунка: `NES_phase = MSX_phase & 1`. Для гибели прямого соответствия по двум парам недостаточно: NES `08` имеет пять фаз, `0B` три, смертельное падение `02` две. Следует выбирать причину смерти и вести NES-визуальный счётчик либо нормализованное время эффекта; две репрезентативные картинки в листе не заменяют полный эффект.

Состояния MSX 0/1 — стоит/идёт, 2 — прыжок, 3 — обычная двухколоночная лестница, 4 — вертикальные верёвки/шест и другие контексты лазания, 5/6 — падение, 7 — отпускание верёвки, 8 — гибель, 9 — исчезновение/возрождение, A — смертельное падение. Состояние 3 подтверждено входами `$hs_897C` (вниз от `10/11`) и `$hs_8986` (вверх от `88/89`) и клавиатурным прогоном `joe-scenes.js`: подпись «цепь» в первоначальном разборе была ошибкой. Важная деталь селектора: 0/6/7 попадают в общий выбор нулевой ходовой позы; 8/A не обновляются в `$92DC`, их кадры задают обработчики. В состоянии 3 флаг `$705F & $40` может на один вызов сохранить прежний MSX-кадр; NES-селектор при входе сразу выбирает лестницу. Дополнительные пары состояния 9 — `68/CC,68/D0` из `$939E`; смертельное падение A использует белый одиночный `78`, а не пару `64/C8`. Поэтому таблица из 15 пар не является полным автоматом героя.

`ps_names` `0C–28` — восемь фаз черепа; предлагается выбирать NES-фазы `0,1,3,4,6,7,9,10`, сохраняя восьмифазную логику порта. Это приблизительное соответствие поворота, его лучше оценить в движении. `2C/30` — две позы MSX-паука против восьми NES: начальный выбор NES `0/4`, либо отдельный визуальный счётчик восьми фаз. **`68` и `78` в `ps_names` не являются дополнительными видами врагов**: 68 входит в кадры исчезновения/возрождения (`939E`), 78 — одиночный белый спрайт гибели от падения (`8B6E`). В JSON это отмечено отдельно. Логику врагов ради новых фаз менять не требуется.

Все перечисленные в задании предметы в NES присутствуют. MSX `20/21/22/23` → NES драгоценность/факел/меч/амулет; `24/25/26` → синий/красный/белый ключ (`06/07/05` NES); `27/28` → змея в двух направлениях. Важные различия — новая мышь, спрайтовая змея, иное число фаз врагов, крупные эффекты гибели, открытые двери 24×32 и другое число строк игрового поля. Утверждать отсутствие других редких объектов на основе одного стартового снимка оснований нет; таблицы и все комнаты выгружены для дальнейшей сверки.

## Летучая мышь

Разобран именно локальный ROM, без внедрения в порт. Адреса ниже — 6502. Отдельная проверка `verify_bat.py` исполняет исходные процедуры: 1600 шагов таймера, пять точек вылета, 24 случая приближения (включая переполнение), четыре обращения к RNG и обе постановочные траектории. Результат — `data/bat_verification.json`.

### Таймер и живой замер

Главный цикл `$C57F` опрашивает контроллер (`$8878`), вызывает логику (`$B96A`), обработчики объектов (`$C47D`), звук (`$86C6`), затем ждёт флаг `$02`, снимаемый NMI. Ветка игры `$B9AE` вызывает `$BC24` **один раз за активный игровой шаг** при сцене `$07C9=1` и отрицательном `$07FD` (игра не на паузе). Это не независимый таймер NMI: при паузе/перестройке комнаты время игры останавливается или выполняется другой путь.

Инициализация `$07C5:$07C4=7:$3F` есть в `$B946`, `$BDC9` и `$C0EC`; последняя выполняется при установке врагов после входа/перерисовки комнаты, включая возрождение. `$BC24` пропускает счёт при `$079A=$0A` и при нулевом `$07C5`. Сначала уменьшается младший байт; старший уменьшается **при переходе младшего 00→FF**. Поэтому задержка равна **64 + 6×256 = 1600 шагов**, а не значению обычного 16-битного числа `$073F`. Это **26⅔ секунды при 60 Гц**, около 26,62 с при частоте NTSC NES.

Номера кадров отсчитываются callback-сценарием после autoboot MAME. Точные события и суммы реальных `DEC $07C4` записаны в `live/*/events.tsv` и `trace.tsv`:

| Опыт | Последняя инициализация | Вызов `$B1FF` | Активных уменьшений после инициализации |
|---|---:|---:|---:|
| стоять (`idle`) | 61 | 1661 | 1600 |
| шаг вправо и обратно (`move_timer`) | 61 | 1661 | 1600 |
| пауза на 120 кадров (`pause_timer`) | 61 | 1781 | 1600 |

Движение таймер не сбрасывает. Смена комнаты и возрождение сбрасывают: это видно и по коду, и по повторным записям из `$C0EE` в маршруте `neighbours`; после уноса мышью в `idle` новый сброс — кадр 2024. Начальные подготовительные сбросы до кадра 61 не являются началом окончательно загруженной комнаты. Событие запуска записывается перед созданием объекта; первый видимый кадр мыши в `idle` — **1664**, в опыте с паузой — 1784. Задержка появляется из-за сборки OAM и DMA, поэтому эти номера нельзя отождествлять с вызовом `$B1FF`. По сохранённому `frame_period=0.016639267340` задержка 1600 активных кадров равна 26,622827744 с.

`$079A` — **этаж пирамиды**: 1–9 обычные этажи, `$0A` сокровищница, 0 переходная сцена нового уровня. Это не номер позы Джо. `$0799` — сложность/номер прохождения; в процедурах таймера и обычного полёта мыши она не читается.

`$079E` устанавливается переходами `$9C50–$9CD2`: 1 — Джо вошёл слева (выход из предыдущей комнаты направо), 2 — вошёл справа, 3 — сверху, 4 — снизу; 0 — начальное/обычное возрождение после завершения сценария. Мышь вылетает со стороны входа:

| `$079E` | X, Y якоря объекта |
|---|---|
| 0 | `$78,$1F` |
| 1 | `$08,$1F` |
| 2 | `$E8,$1F` |
| 3 | `$78,$1F` |
| 4 | `$78,$F0` |

Экранный Y спрайта дополнительно учитывает смещение части и аппаратное `+1`. Значения вне 0–4 код не обрабатывает.

### Полёт, контакт и постановочные сцены

Обычная мышь (`$B1FF`, обработчик `$B2BE`, флаг `$8E+slot=$04`) выбирает случайную промежуточную цель возле **текущего** Джо. Смещение X — 0–31 в случайную сторону; Y — всегда 0–31 **выше** Джо. В `$B32F` действительно записывается вариант `heroY+offset`, но затем выполнение проваливается в `$B332`, безусловно заменяющий его на `heroY-offset`. Четвёртый вызов RNG всё равно происходит. Это особенность исходной программы; перенос «случайно вверх или вниз» изменит поведение.

Мышь идёт к цели по одному пикселю по каждой оси за активный шаг. Диагональ имеет скорость √2 пикселя/шаг. Достаточно попасть в координату цели или на один пиксель правее/ниже неё. Затем выбирается новая цель. Сравнения беззнаковые, арифметика байтовая: путь через границу не выбирается по кратчайшему расстоянию. Стены и лестницы не проверяются — мышь летит сквозь них. Обычный полёт не имеет срока жизни, не усиливается по сложности. Таймер после запуска остаётся нулевым: второй обычной мыши до сброса комнаты не будет.

Есть дополнительная тонкость `$B3A2/$B3B2`: промежуточный `$9F` обновляется только при X-разности 00/FF; иначе сохраняется прежнее значение. Именно его проверяет Y-процедура при решении закончить сближение. Ниже этот эффект сохранён, а не заменён идеализированным условием «обе оси рядом».

Столкновение проходит через `$A47D`. Пока `$07B9!=0` (защита амулета), проверка врагов пропускается. Младшие два бита флага мыши равны нулю, поэтому ветка `$A4EF→$A4F7` выполняется **раньше поиска меча**. Меч от мыши не защищает. Мышь получает флаг 08 и цель `(heroX−1,heroY−7)` (`$B33B`), а Джо — `$0784=$80`, заморозку текущей анимации `$3A=1` и режим смерти `$0790=4`. После сближения мышь летит вверх по одному пикселю/шаг; `$A770` синхронно уменьшает Y Джо. После байтового Y Джо `$EE` запускается обычное исчезновение/возрождение. `$ABF8` уменьшает число оставшихся жизней `$07BE`, если оно ненулевое. В этом пути нет удаления предмета из `$D3–$D7` и нет начисления очков; ветка награды `$A53C` не вызывается.

При Y мыши `$FB` `$B2BE` назначает **самой мыши** пустой кадр Джо `09` из `$D738`. Это не назначение позы Джо: X всё ещё указывает на слот мыши. Явного освобождения слота здесь нет; он очищается при перестройке комнаты. Без неё обработчик продолжает менять байтовый Y уже невидимого объекта.

Два иных запуска не используют таймер/преследование:

- `$B268` из `$996F`: переходная сцена нового уровня, `$079A=0`, фаза сценария `$07CE=2`. Начало `(0,$65)`, обработчик `$B44A`, сценарий `$D32F`: 8 шагов `(x+2,y+2)`, затем 67 `(x+2,y−2)`. Всего 75 шагов, итог `(150,239)` (байтовый Y соответствует −17).
- `$B293` через `$98C8` из `$989E`: постановочный эпизод сокровищницы, ветка `$079A=$0A`, `$07CE=2` (см. `$A731`). Начало `($15,$BB)`, обработчик `$B3D0`, сценарий `$D328`: 41 шаг `(x+2,y−2)`, 27 шагов ожидания, 69 шагов `(x+2,y+1)`. Всего 137 шагов, итог `(241,174)`.

Обе процедуры назначают анимацию `$D990`, обнуляют `$07CC`, ставят `$07CD=$FF`; флаги столкновения и направление явно не устанавливают, полагаясь на состояние выделенного слота. Конец сценария устанавливает `$07CC=$FF`; освобождения слота в этих обработчиках тоже нет. На следующий кадр после 75/137 движущих/ожидающих шагов обрабатывается терминатор.

### Псевдокод для переноса

Все координаты, счётчики и результаты `+/-` ниже — `uint8` с оборачиванием; индексы и перенос сравнения — отдельно. Массивы объектов: `x=$10+s`, `y=$16+s`, `state=$1C+s`, `dir=$40+s`, `turn=$46+s`, `handler=$82/$88+s`, `flags=$8E+s`. Глобальные: `active=$07C6`, `targetX/Y=$07C7/8`, `scriptPC=$07CC`, `scriptCount=$07CD`, временный `scratch=$9F`. Эти поля **не отдельные для каждой мыши**.

```text
BC24 tick_timer():
    if floor[079A] == 0A or timerHi[07C5] == 0: return
    timerLo[07C4]--
    if timerLo == FF:
        timerHi--
        if timerHi == 0: B1FF_spawn()

C566 allocate():
    return first slot 0..5 whose [76+s] == FF, else 6
    # B1FF/B268/B293 не проверяют 6; при переносе это предположение
    # оригинала, а не безопасный контракт аллокатора.

B1FF_spawn():
    s = C566_allocate(); currentSlot[9B] = s
    flags[s] = 04
    if entry[079E] in 0..4: (x[s],y[s]) = spawnTable[entry]
    handler[s] = B2BE; turn[s] = 0; dir[s] = 1
    C355_set_animation(s, table=D990, state=0)
    active = 0

8000_random():
    lo = [A9]; hi = [AA]
    repeat 8:
        carry = bit7(lo); lo = lo << 1
        overflow = bit7(hi); hi = (hi << 1) | carry
        if overflow: lo ^= 39
    [A9] = lo; [AA] = hi
    return lo

B2FB_choose_target():
    scratch = random() & 1F
    if random() < 7F: targetX = heroX + scratch
    else:             targetX = heroX - scratch
    scratch = random() & 1F
    sign = random()                 # потребляется даже при перезаписи Y
    if sign < 7F: targetY = heroY + scratch
    targetY = heroY - scratch       # реальная безусловная запись B332

B3A2_filter_x(delta):
    if delta == FF: scratch = FF; return FF
    if delta == 00: scratch = 00; return FF
    return delta                   # scratch остаётся прежним

B3B2_filter_y(delta):
    if delta not in {00,FF}: return delta
    if scratch in {00,FF}: active = 0
    return FF

B355_approach(s):
    delta = targetX - x[s]
    increase = (targetX >= x[s])    # перенос SBC, беззнаковое сравнение
    if B3A2_filter_x(delta) != FF: x[s] += (1 if increase else -1)
    delta = targetY - y[s]
    increase = (targetY >= y[s])
    if B3B2_filter_y(delta) != FF: y[s] += (1 if increase else -1)

B2BE_update(s):
    if flags[s] & 04:
        if active == 0: B2FB_choose_target(); active = 1
        B355_approach(s)
    else:
        if active != 0: B355_approach(s)
        else:
            y[s]--
            if y[s] == FB: C355_set_animation(s, D738, 09)

B33B_capture(s):
    flags[s] = 08; active = 1
    targetX = heroX - 1; targetY = heroY - 7

A4F7_contact(s):
    B33B_capture(s)
    [0784] = 80; heroAnimationCountdown[3A] = 1; [0790] = 04

A770_carry_hero():
    if [0784] & 80:
        if active == 0: heroY--
        if heroY == EE: [0782] = F0; [0784] = 0
    else:
        A794_normal_death_countdown_and_respawn()

B268_intro_spawn():
    s = C566_allocate(); currentSlot = s
    (x[s],y[s]) = (00,65); handler[s] = B44A
    C355_set_animation(s,D990,0); scriptPC=0; scriptCount=FF

B293_treasure_spawn():
    s = C566_allocate(); currentSlot = s
    (x[s],y[s]) = (15,BB); handler[s] = B3D0
    C355_set_animation(s,D990,0); scriptPC=0; scriptCount=FF

B3D0_treasure_update(s): execute_script(s,D328,{07:(+2,-2),08:(+2,+1),01:(0,0)})
B44A_intro_update(s):    execute_script(s,D32F,{07:(+2,+2),08:(+2,-2)})

execute_script(s,table,moves):
    command = ROM[table + scriptPC]  # FF не является допустимым движением
    if command not in moves: scriptPC=FF; return
    if scriptCount == FF: scriptCount = ROM[table + scriptPC + 1]
    (dx,dy) = moves[command]; x[s]+=dx; y[s]+=dy
    scriptCount--
    if scriptCount == 0: scriptPC+=2; scriptCount=FF

D328 = 07 29 01 1B 08 45 FF
D32F = 07 08 08 43 FF
```

Анимация обслуживается общим `$C3BB`: восемь ссылок `$D97A`, задержка 4. Полёт не меняет `dir=1`, то есть мышь обычно показывает один и тот же вариант отражения даже при движении влево. Для точного порта нужно сохранить порядок вызовов RNG/объектов и байтовую арифметику; для собственного поведения можно осознанно устранить перезапись Y и зависимость от старого `$9F`, но это будет изменением игры.

## Предложение для Вектора — без внедрения

Для первого варианта предлагается **Джо в двух цветах `06/27`, высота 19 строк**, с теми же нижней точкой и X-якорем, что у нынешнего Джо. Светлый красный `26` объединяется с `27`; тёмный контур `06` сохраняется. В `joe_choices.png` показаны все непустые кадры в двух/трёх цветах, с натуральной занятой высотой и ужатием до 19 строк. Это ближайший сосед без сглаживания; для окончательной графики лицо, края шляпы и ступни стоит поправить вручную.

Натуральный вариант обычных поз — 16×22, лестница/канат — 16×23. При сохранении ног верх выступает на 3–4 строки выше нынешней рамки 16×19. Кроме высоты меняется занятая ширина: было 12, становится 16 точек. Координатная логика столкновений останется прежней, но шляпа и плечи могут визуально заходить в соседние тайлы. Нельзя масштабировать отдельно обрезанные кадры без сохранения якорей: в JSON даны и рамка частей, и рамка непрозрачных точек. Эффекты 32×32 требуют отдельного решения для вывода/области восстановления; в первом внедрении их разумно перерисовать в пределах поддерживаемой рамки.

Три цвета сохраняют NES `06/26/27` и лицо/рубашку лучше. Для третьего непрозрачного цвета нужен ещё один индекс, например 2, уже используемый комнатой: тогда либо меняется акцент кирпичей, либо рубашка перекрашивается вместе с этажом. Макеты показывают первый компромисс: 2 фиксируется под `26`, комнатный акцент уступает ему. Двухцветный вариант оставляет индекс 2 акценту NES-этажа.

Предлагаемая схема восьми индексов (после округления NES RGB до DAC Вектора):

| Индекс | Цвет / назначение | Ограничение |
|---|---|---|
| 0 | чёрный | фон |
| 1 | `27`, кожа Джо | может разделяться с тайлами |
| 2 | акцент этажа; для 3 цветов Джо — `26` | разделяется с комнатой |
| 3 | `06`, тёмный Джо/кирпич | общий с комнатой |
| 4 | `20`, белый врагов | OR-плоскость поверх 0 |
| 5 | `20` | OR поверх 1 |
| 6 | `1C`, сине-зелёный комнаты | одновременно результат OR поверх 2 |
| 7 | `20` | OR поверх 3 |

Это укладывается в восемь индексов, но не воспроизводит одновременно все палитры NES. У врага, рисуемого OR 4, отображение неизбежно `0→4,1→5,2→6,3→7,6→6`: на акценте 2 череп станет сине-зелёным, а на уже выставленном бите 4 цвет не изменится. В макетах используется именно эта операция, конфликт не скрывается отдельным полноцветным наложением. Можно отдать 6 белому врага ценой сине-зелёных деталей комнаты, либо впоследствии обсуждать другой способ вывода врагов. Здесь такого изменения нет.

Формат DAC: `BBGGGRRR`, компоненты округляются к 3/3/2 битам; предпросмотр использует идеальные уровни 0..255 без модели аналогового тракта Вектора. `vector_proposals.json` содержит байты, RGB, варианты и размеры, `vector_floor_palettes.json` — предложение для всех девяти этажей с двухцветным Джо. Это светлые палитры; для темноты следует отдельно скрывать пиксели комнаты, оставляя Джо, поскольку глобальное обнуление разделяемых цветов 1/3 скроет части героя.

Созданы восемь макетов 256×192: по четыре для старта `(0,10)`, индекс 2, и `(1,9)`, индекс 5. Имена `room_02_2colors_22rows.png`, `room_02_2colors_19rows.png`, `room_02_3colors_22rows.png`, `room_02_3colors_19rows.png`, аналогично `room_05_*`. Рядом — `_indices.png` с индексами 0..7, а не RGB; `overview.png` объединяет варианты.

Макеты сохраняют **геометрию MSX**: заменены кирпич и Джо, враги показаны NES-силуэтами с ограничением OR, остальные лестницы/предметы/огонь используют существующие MSX-маски с выбранными цветами. HUD не рисовался, верхние 40 строк пустые. Это эскиз первого этапа переноса, а не законченная перерисовка всех фоновых тайлов и не снимок работающего нового рендера.

## Оставшиеся решения

- По решению владельца 28.10 выбран натуральный Джо: 16×22, лестница 16×23, без вертикального масштабирования. Реализация, исправленный выбор лестничных кадров и замеры — `docs/JOE_NES.md`, раздел 4.
- Решить, нужна ли мышь NES как новый враг: её рисунок извлечён, но логика MSX её не содержит.
- Выбрать компромисс цветов 2/6 при прежнем OR-выводе врагов; трёхцветный Джо дополнительно конкурирует с акцентом комнаты.
- Раскладку NES нельзя вставить вместо MSX без переделки координат. Следующий этап фоновой графики — рисунки в нынешней сетке, с отдельной адаптацией открытых дверей и крупных эффектов.
- Слот комнаты 99 и фактические задержки огня при фоновой нагрузке не интерпретированы сверх описанной проверки. Табличные фазы, код и исходные данные сохранены, так что это не препятствует работе над Джо.
