# Прямой вывод нативной сборки

## План (27.10.2026)

Логика и её ОЗУ 7000–73FF остаются эталонными. VNT — карта игры.
Вывод получает координаты и кадры непосредственно из записей объектов игры;
таблица порядка 72E0 задаёт перекрытие. Джо — объект с двумя слоями,
у которых общая область сохранения фона. Спрайты выводятся в начале прерывания.

1. Убрать копирование SAT. Хранить дескрипторы размещения и готовой графики
   объектов между выводами; менять их при изменении координат, кадра или слоя.
   Повторное рисование из-за фона использует прежний дескриптор. Враги —
   вертикальные полосы готового сдвига (8000, OR); слои Джо — маски A000/C000.
2. Вместо регистров — разрешение вывода, запрос полной перерисовки, кадр огня
   и кадр ленты. Все кадры лент — неизменяемые данные. Живые клетки — по
   спискам комнаты; лента всегда целиком, огонь сохраняет FIRE_K=3.
3. При смене комнаты/цветов строить готовую графику тайлов: три полосы по
   восемь байт, в порядке 8000/A000/C000. Рисование клетки — копирование
   готовых полос. По возможности разделять одинаковые полосы/образы,
   чтобы не уменьшать число готовых сдвигов врагов.
4. Удалить оставшиеся VDP-структуры, мёртвые процедуры и привязанные к ним
   проверки; сохранить независимый эталон пикселей и lockstep ОЗУ.
5. После удешевления подготовки — ожидание кадра, обработчик логики,
   подготовка вывода. Фазы лент и огня, очередь врагов, Джо при изменении.
   Если crit ещё ожидает прерывания, новая подготовка не начинается.

## Проверки каждого этапа

Обычная и STRICT сборки; slsall (три уровня и обход); scrchk 2000 шагов
в обычной игре, r19 и tp; FANY=1 cellchk 3000 tp; r19b; nsteps; pschk.
В итог также входят rsplit и обновлённые образы ROM.

объекта из-за изменённого фона не пересчитывает его дескриптор.

### Этап 3: готовые образы тайлов комнаты

Нативная сборка получила отдельную карту памяти (src/native/mem.asm).
E000–EBFF — 128 образов по 24 байта; EC00–EEFF — очередь клеток PND;
F300 — соответствие тайлов образам. Стек прерывания занимает бывшую SAT
(вершина 7F80), отдельно от цветов 7F80–7F9F.
Исходные полосы дедуплицируются генератором mkvideo.py: 154 полосы,
1232 байта. Все четыре варианта живого тайла строятся одновременно;
кадр выбирает готовый образ. Цвет изменился — перестраиваются только
уже используемые образы этой группы. При необычно большом наборе
кэш безопасно сбрасывается; экран от этого не меняется.

Рисование клетки больше не разбирает цвет и режимы. Таблицы режимов
всех 256 сочетаний цвета и копий банков нет; 32 режима групп используются
только при построении готовой графики и выборе изменившихся плоскостей.
Пиксельный эталон теперь независимо разворачивает исходные снимки MSX
(video-ref.js), не читает кэш готовой графики Вектора.

Обе сборки и проверки прошли: scrchk 0 (1186/238/1153), cellchk 0 (291),
lockstep — норма. 1,9: 1,337 кадра/шаг, **37,4 шага/с**; обычная игра
41,9; rsplit — 16 смен, 586 шагов/950 кадров возле смен, обычный шаг
1,08 кадра (46,2 шага/с). Готовых сдвигов **59/96**.
Стоимость всего вывода пока остаётся высокой; следующий этап — очистка
оставшихся старых структур, затем распределение работы по шагам.

### Этап 4: удаление старого слоя

память видеочипа. Палитра Вектора по комнате сохранена.
Удалены неиспользуемый просмотрщик и старые проверки echk/mchk/crchk/npair.
Генератор ресурсов создаёт только используемые нативные исходники;
необязательная сверка PATS в lockstep также понимает прямые кадры.
Свободная страница EF00–EFFF отдана готовым сдвигам врагов.

Обе сборки и все проверки прошли. scrchk 0 (1180/233/1160), cellchk 0
(290), lockstep — норма. 1,9: 1,333 кадра/шаг, **37,5 шага/с**;
обычная игра 42,0. rsplit: 16 смен, 586 шагов/948 кадров возле смен,

### Этап 5: фазы, постоянное покрытие клеток и исходники объектов

frame_wait ждёт событие кадра, выполняет frame_handler и начинает
подготовку, только если предыдущий crit уже исполнен. События кадра —
короткая очередь до двух, чтобы длительная подготовка не теряла сразу
два события. Ожидания завершения crit внутри подготовки нет.
Ленты и огонь чередуются, враги 2–4 выбираются по очереди, четвёртый
враг проверяется дополнительно; Джо проверяется на каждом выводе.
Объединение двух слоёв Джо строится только при изменении его дескриптора.

Биты 1–6 в PND постоянно описывают покрытие клеток слоями объектов;
бит 0 остаётся очередью. Изменение клетки сразу отмечает покрывающие её
объекты. Не нужны два обхода всех прямоугольников на каждый вывод.
Смена фона A000/C000 не требует перерисовки врагов из 8000. Покрытие
не пересчитывается при повторном выводе в том же прямоугольнике.
Для частых наборов плоскостей есть прямые входы копирования без цикла.
Огонь перебирается сразу с шагом FIRE_K, без посещения пропущенных клеток.
Списки тайлов, изменяющихся между фазами, готовит mkvideo.py.

Исходники спрайтов теперь имеют таблицу указателей на 42 различных
кадра вместо копии таблицы шаблонов MSX. Свободный хвост 79C0–7BFF
отдан готовым сдвигам. Кэш тайлов уменьшен до 120 образов; его хвост
EB40–EBFF также отдан сдвигам. Сброс при исчерпании кэша сохранён.

Эталон проверяет показанные fire_shown/belt_shown даже при ожидании
следующей фазы игры; запрос новой анимации больше не исключает экран
из проверки. Неизменные исходные снимки MSX по-прежнему задают каждый
ожидаемый пиксель. Комната, цвета и незавершённый crit по-прежнему
исключаются, пока вывод их не закончил.

Обе сборки и полный набор проверок прошли: lockstep — норма;
scrchk 0 (815/123/735), cellchk 0 (425). **1,9: 1,018 кадра/шаг,
49,1 шага/с**; обычная игра 41,9. rsplit: 17 смен, 572 шага/1051 кадр
возле смен, обычный шаг 1,03 кадра (48,4 шага/с). Сдвиги **75/96**.
Распределение 601 шага: 0 кадров — 260, 1 — 76, 2 — 259, 3 — 6.
Цель ровного шага в каждом кадре ещё не достигнута; работа продолжается.

### Этап 6: прерывания при копировании клеток

Копирование живых и обычных клеток больше не меняет SP и не выполняет
DI/EI. Клавиатура, палитра и crit остаются в начале прерывания.
Причина: на Векторе импульс IRQ, пришедший при DI, теряется; сокращение
копирования через стек экономило такты, но иногда теряло сам кадр.
Текущая очередь кадров ограничена восемью событиями (страховка длинных
смен комнат); каждый обработчик потребляет ровно одно событие.

Полный набор проверок прошёл: обе сборки, lockstep — норма;
scrchk 0 (795/142/749), cellchk 0 (418). **1,9: 1,000 кадра/шаг,
50,0 шага/с**; обычная игра 43,5. rsplit: 17 смен, 587 шагов/986 кадров
возле смен, обычный шаг 1,01 кадра (49,4 шага/с). Сдвиги **74/96**.
Средний темп достигнут. Распределение 600 шагов: 0 кадров — 275,
1 — 59, 2 — 259, 3 — 5, 4 — 2; это ещё не ровный шаг в каждом кадре.

### Этап 7: нативные полосы врагов и проверка плавности

Враги используют только постоянный дескриптор L/столбец/высота/пустые
столбцы и указатель готового сдвига. Сохранение фона объединено с OR;
таблицы PPS/PPD/RST для врагов не строятся. Общий механизм оставлен для
двух слоёв Джо. Если полосы объектов по Y независимы, это доказывается
по их рамкам; порядок действий кэшируется до изменения Y/видимости.
Для одиночного изменения отсутствие пересечений проверяется по покрытию.

Таблица rot_tab удалена. При построении масок выбирается короткая цепочка
RRCA, а 6900–6DCF занимают неизменяемые исходные полосы тайлов; хвост
до 7000 — готовые сдвиги. Таблица входов полос строится ассемблером.
E0–EF имеют заранее подготовленные варианты цветов A0/00/40; цветовые
переходы обновляют только изменившиеся группы и плоскости. Две переменные
плоскости получают общую исходную полосу за одно чтение каждого байта.

Исправлена адресация кэша: шаг образа равен **24**, а не 32 байтам.
При большом числе тайлов прежняя формула могла затереть готовые сдвиги.
Новый native-video.js проверяет каждый готовый сдвиг по исходной графике
MSX и запрещает последующую запись в его память. Эталон экрана также
учитывает восьмибитное переполнение Y+1 (атрибут FF означает строку 0).
Оба пиксельных стенда теперь возвращают ненулевой код при ошибке.

Вместо безусловного пропуска двух врагов проверяется накопленное смещение.
При задержке катящийся враг выбирает промежуточную позицию на своей
горизонтальной траектории, максимум в трёх пикселях от нарисованной;
игровые координаты не меняются. Рамка покрытия соответствует именно
показанной позиции. За 1000 шагов максимум скачка всех трёх врагов — 3,
максимальное отставание от координаты игры — 6 пикселей. Проверка также
контролирует пройденное расстояние, чтобы ограничение скачка не превращало
движение в постоянное замедление.

Обе сборки и полный набор проверок прошли: четыре строки lockstep — норма;
scrchk 0 (662/31/449 проверок), FANY cellchk 0 (408).
**1,9: 0,993 кадра/шаг, 50,3 шага/с**; обычный сценарий 43,6;
rsplit: 17 смен, 589 шагов/991 кадр около смен; обычный шаг 1,01 кадра,
49,7 шага/с. Готовых сдвигов **78/96**. Дополнительный обход 6500 шагов
проверяет больше комнат; длинный контроль памяти сдвигов — 3000 шагов.

На 1000 шагов/1004 физических кадра: 218 смен показанной фазы огня,
249 смен фазы ленты. Огонь — 10,9 смен/с против исходных 9,4 (251 смена
за 1342 кадра); FIRE_K=3 сохранён, ленты всегда целиком.
Разбиение огня на слишком маленькие порции отвергнуто: оно уменьшало
частоту анимации. В этой версии порция FIRE_K завершается полностью.

Средняя скорость достигнута, равномерность — ещё нет: из 600 шагов
234 идут через 0 кадров, 140 через 1, 222 через 2, 4 через 3.
Очередь событий кадра всё ещё компенсирует отдельные длинные подготовки.
Для строго одного шага на каждый кадр нужен отдельный этап уменьшения
пиков, а не только средней стоимости.

### Этап 8: готовые адреса живых клеток и короткие цветовые переходы

Список живых клеток хранит готовый младший байт экранного адреса
в F500–F5FF. Старший байт определяется столбцом карты; повторного
вычисления строки на каждой клетке нет. Для одной меняющейся плоскости
добавлен прямой вход копирования. При изменении только лент/лазеров
очищаются их 16 флагов вместо всей страницы. На таблицу адресов отдана
одна страница, число готовых сдвигов остаётся выше исходного: 68/96.
Исходники ресурсов заново созданы mknative.py, обе сборки воспроизводятся.

Обе сборки, полный набор проверок и контроль native-video 3000 пройдены.
Расширенный scrchk проверяет экран также сразу после crit. Если записи
dlist устарели, отсутствие ожидающих клеток определяется по биту 0 PND,
поэтому такие записи больше не скрывают экран от проверки. Пиксельное
сравнение не менялось; до первого L_A5D1 меню, как и раньше, не проверяется.
scrchk: 0 неверных экранов (1398/946/1384 проверок в обычной игре/r19/tp),
FANY cellchk 0 (417). ОЗУ и VNT/цвета сверены с MSX по четырём прогонам.
Дополнительный обход 6500 шагов: 3835 проверок экрана, 0 ошибок.
Проверка непосредственно из IRQ потребовала различать незавершённую запись
карты/цветов и законченное изменение: IRQ может прийти после записи байта,
но до установки флага уведомления. video_edit отмечает эту короткую операцию.
Исходные снимки на L_A5D1 сохраняются; стенд отдельно требует video_edit=0
в каждой такой точке. Исключаются только дополнительные снимки IRQ,
попавшие внутрь операции. Это устранило ложное сравнение нового цвета
с ещё прежним экраном при обходе нижних комнат.

Средняя скорость 1,9 — **50,3 шага/с** (0,993 кадра/шаг).
Распределение 601 шага: 0 кадров — 236, 1 — 133, 2 — 232.
Попытки ограничить очередь одним IRQ и принудительно выбирать одного
или двух врагов на подготовку не приняты: они давали менее 50 шагов/с
либо отставание движения. Мелкие порции огня также не приняты из-за
снижения частоты анимации. Сохранены полная порция FIRE_K=3 и целая лента.

За 2800 шагов/2804 физических кадра контроль сдвигов не обнаружил

## Что остаётся

VDP-слой нативной сборки удалён, средние 50 шагов/с достигнуты.
**Строго один шаг в каждом физическом кадре не достигнут.**
Пики подготовки по-прежнему компенсируются очередью событий; это видно
в распределении 0/2, хотя максимум движения катящихся врагов ограничен
тремя пикселями. Смена комнаты тоже остаётся длинной операцией.
Общий механизм сохранения двух перекрывающихся слоёв Джо оставлен:
он нужен для корректного перекрытия; независимые враги уже обходятся
без него. Уменьшать частоту анимации и целостность лент ради ровного
графика не стали. Поэтому считать требование равномерности выполненным
по одному среднему FPS нельзя.
